# Рабочий процесс Threads — проект для настройки

Статус: PROPOSED / AWAITING_USER_PREFERENCES. Это спецификация, а не запущенная автоматизация.
Подготовлено 20 ноября 2026 года по Asia/Vladivostok.

## Результат для пользователя

Пользователь даёт направление, получает готовые тексты с картинками и временем, одобряет выбранные публикации. Дальше исполнитель планирует одобренное и проверяет результат. Раз в неделю пользователь получает короткий отчёт и предложения на следующую неделю. Пользователь не переносит файлы между чатами на постоянной основе.

## Один ответственный исполнитель

Весь цикл ведётся в одном пользовательском чате с работающим Metricool. Предложенный чат — «автоподключение Threads Codex»; выбор ещё уточняется у пользователя. В этой среде 20 ноября инструменты Metricool и создания повторяющихся задач не найдены. Подключение в другом чате нужно проверять там.

GitHub хранит задания, согласования и результаты. Commit/push сам по себе не запускает другой чат, не создаёт фоновую задачу и не передаёт авторизацию. Не обещать автоматическую доставку уведомлений между чатами.

Разовая настройка исполнителя неизбежна, если у текущего чата нет инструментов. После неё контент и согласования остаются в выбранном чате; не заставлять пользователя ежедневно обращаться к разным агентам.

## Согласование

- По действующему правилу каждый пост требует явного согласия на точные текст, вложения, аккаунт и время. Нельзя публиковать неподтверждённое.
- У пользователя уточняется удобная форма: подтвердить весь показанный пакет заранее либо подтверждать отдельный пост перед выходом. Пакетное подтверждение допустимо только если пользователь выбрал такой режим и прямо одобрил весь конкретный пакет.
- Вопросы заданы в текущем чате. Ответы ещё не получены; не считать рекомендованные варианты выбранными.
- Если выбран поштучный режим, неподтверждённый пост остаётся локальным черновиком. Не создавать автоматически публикуемую запись в Metricool до согласия. Ожидание согласия у исполнителя должно реально поддерживаться средой, иначе не обещать запрос в точное время.
- Предлагаемый шаблон после выбора пакетного режима: «Одобряю пакет YYYY-MM-DD целиком для @nickkem_vl по указанному времени» или «Одобряю 1, 3 и 5; в остальных нужны правки».
- Для каждого одобрения сохранять перечень ID, версию/хеш контента, дату, точную фразу пользователя. Хеш включает аккаунт, время, текст и порядок медиа. Изменение этих полей требует повторного согласования именно изменённых постов.
- Разрешение собрать пять постов не равно разрешению их выпустить. При отсутствии ответа, ошибке или истёкшем времени пропустить публикацию и сообщить пользователю. Не отправлять её позже без одобрения нового времени.

## Ежедневный цикл

1. Прочитать свежий main, общие правила и результаты прошлых постов. Проверить фактический аккаунт в Metricool.
2. Подготовить пять самостоятельных коротких постов: разные темы, часть с картинками, часть без. В качестве начального предложения — три визуальных и два текстовых. Это предложение, не установленная ежедневная норма.
3. Выбрать пять разных минут внутри одобренного временного окна, с достаточными промежутками. Неровные минуты нужны для распределения и тестирования. Не представлять автоматизацию как доказательство присутствия автора онлайн.
4. Показать один пакет: полные тексты, картинки в порядке публикации, профиль, календарную дату, часовой пояс и время. Указать ID пакета и версию.
5. Получить согласие согласно выбранному режиму. Обновить согласование, проверить оставшуюся квоту Metricool и отсутствие дублей. Не оплачивать тарифы без поручения.
6. Использовать актуальные инструменты Metricool, следуя навыку. При неясном результате записи сначала проверить очередь. Не повторять запись вслепую.
7. Сохранить действительные ID и время для запланированного поста. Подтверждение выхода и ссылку записывать отдельно. Наличие записи в очереди — статус SCHEDULED, а не PUBLISHED.
8. Показать пользователю короткую квитанцию: какие посты запланированы/опубликованы/пропущены. Не отправлять сообщения через сторонние каналы без отдельного поручения.

## Статусы и защита от повторов

Для отдельного поста: DRAFT → AWAITING_USER_APPROVAL → APPROVED → SCHEDULED → PUBLISHED.
Дополнительные статусы: CHANGES_REQUESTED, BLOCKED, FAILED, SKIPPED, CANCELLED.
Статус не означает наличие автоматического обработчика. Записи содержат ID задачи, хеш одобренного предложения, свидетельство согласия, ID/UUID Metricool, время, подтверждённую ссылку и последнее сообщение об ошибке.
Один ответственный исполнитель изменяет очередь. Перед повторным запуском он читает актуальные данные сервиса и GitHub. Уже опубликованный первый пост не повторять.

## Еженедельный отчёт

Предложение: понедельник, 10:13 по Владивостоку. День/время ещё не согласованы. Период — предыдущая полная неделя, понедельник 00:00 — воскресенье 23:59:59 по Asia/Vladivostok. Первый короткий период отмечать отдельно.

- Сколько постов вышло, сколько пропущено и почему; фактические ссылки.
- Просмотры, лайки, ответы, репосты, цитирования, распространения, динамика подписчиков — только доступные метрики с актуальными определениями Metricool. Просмотры не называть уникальным охватом. Подписчиков по дням не суммировать.
- Показать три сильных и три слабых поста, если их достаточно, с темой, временем и наличием изображений. Сравнивать посты сходного возраста; не объявлять тему или время причиной результата по пяти неодинаковым постам.
- Положительные ответы «+», обращения и заказы считать только при наличии доступа к самим комментариям/учёту заявок. Счётчик ответов Metricool не показывает содержание комментариев. При отсутствии доступа запросить у владельца три числа, не выдумывать конверсию и выручку.
- Предложить два-три конкретных изменения на следующую неделю. Изменения контента не отменяют согласование будущих постов.
- Пустая выдача или задержка синхронизации не означает нулевой спрос. В отчёте указывать ограничения данных.

## Как включить автоматические запуски после уточнений

Приоритет — встроенные повторяющиеся задачи в выбранной среде с доступом к Metricool: подготовка пакета, проверка одобренной очереди/результатов и недельный отчёт. Сначала проверить наличие инструмента создания задач и доступ к Metricool внутри выполнения такой задачи. Подключение приложения в обычном чате само по себе этого не доказывает.

Если такие задачи доступны: создать только согласованное расписание, сохранить реальные ID задач, выполнить пробный запуск чтения и доставки черновика в согласованный интерфейс. Не публиковать тестовый контент для проверки связи. Отчёт и подготовка не должны отправлять письма или сообщения в другие каналы без разрешения пользователя.

Если встроенных запусков нет: можно рассмотреть один внешний исполнитель/сценарий. Пока не регистрировать сервисы, не создавать сервер, не размещать токены и не настраивать платные API. Наличие n8n/Activepieces в локальном каталоге не означает действующего подключения Metricool. Сначала подготовить и согласовать конкретную схему авторизации, запуска и интерфейс подтверждения.

В этой среде автоматические задачи НЕ СОЗДАНЫ. Файлы в GitHub — только подготовленная основа. Не предлагать GitHub Actions как автоматический способ получить сессионную авторизацию MCP из другого чата.

## Проверка перед запуском системы

Нужно получить ответы пользователя на три уже заданных вопроса: режим согласования; дни и временное окно; значение фразы о референсах, основной чат и время отчёта. Затем проверить реальные инструменты и тариф. Пять постов ежедневно — примерно 150–155 в месяц: исторический лимит Free в навыке не покрывает такой объём, но текущую квоту и тариф нужно проверить в аккаунте, ничего не покупать автоматически.

Критерий готовности: в выбранном чате можно получить пакет → подтвердить его один раз в выбранном режиме → получить проверяемые ID и даты публикаций; автоматический отчёт действительно приходит по расписанию. Пока этот путь не проверен, называть систему подготовленной, а не полностью работающей.
